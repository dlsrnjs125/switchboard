# PostgreSQL Table Specification

## Scope and notation

This specification is detailed enough to author Phase 1 Flyway migrations. Column lists omit repetitive constraint names, but migrations must give every PK, FK, unique, check, and trigger a stable explicit name.

See the [ERD](erd.md) for aggregate relationships, the [index strategy](index-strategy.md) for physical access paths, and the [migration policy](migration-policy.md) for rollout and retention rules.

- `PK`: primary key
- `UK`: unique constraint
- `FK`: foreign key
- `NN`: not null
- All UUIDs are UUIDv7 generated by the application unless an import path explicitly preserves an existing identity.
- All customer-owned tables carry `tenant_id`; project-owned tables also carry `project_id`.

## Identity and access

### `tenants`

Source of truth for the top-level isolation boundary.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_key` | `varchar(128)` | NN, UK, Phase 0D key pattern |
| `name` | `varchar(200)` | NN, non-blank |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |

Constraints: `UNIQUE (tenant_key)` and alternate key `UNIQUE (id, tenant_key)` when external imports require it. Tenant hard deletion is forbidden while any owned resource exists.

### `tenant_members`

Maps an external human principal to a tenant-scoped role. The identity provider remains authoritative for the principal itself.

| Column | Type | Rules |
| --- | --- | --- |
| `tenant_id` | `uuid` | PK part, FK `tenants`, NN |
| `principal_id` | `varchar(255)` | PK part, NN; normalized issuer-qualified subject |
| `role` | `varchar(32)` | NN; `TENANT_OWNER`, `PROJECT_MAINTAINER`, `DEVELOPER`, `VIEWER`, `AUDITOR` |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |

The baseline does not store platform-admin authority as a tenant membership and does not use `SERVICE_CLIENT` for human members.

## Authoring

### `projects`

Source of truth for the flag and application namespace inside a tenant.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | FK `tenants`, NN |
| `project_key` | `varchar(128)` | NN, key pattern |
| `name` | `varchar(200)` | NN, non-blank |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |
| `archived_at` | `timestamptz` | nullable |

Constraints: `UNIQUE (tenant_id, project_key)` and `UNIQUE (tenant_id, id)`. Archival does not release `project_key`.

### `environments`

Source of truth for an environment identity and its publication concurrency token.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `environment_key` | `varchar(128)` | NN, key pattern |
| `name` | `varchar(200)` | NN |
| `environment_type` | `varchar(32)` | NN; `DEVELOPMENT`, `STAGING`, `PRODUCTION` |
| `current_snapshot_version` | `bigint` | NN, default `0`, check `>= 0` |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |
| `archived_at` | `timestamptz` | nullable |

Constraints: composite FK `(tenant_id, project_id) -> projects (tenant_id, id)`, `UNIQUE (tenant_id, project_id, environment_key)`, and `UNIQUE (tenant_id, project_id, id)`. Only the publication transaction increments `current_snapshot_version`.

### `feature_flags`

Stable flag identity. Value type is stable for the identity; changing it requires a new flag key.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `flag_key` | `varchar(128)` | NN, key pattern |
| `value_type` | `varchar(16)` | NN; `BOOLEAN`, `STRING`, `NUMBER`, `OBJECT` |
| `lifecycle_status` | `varchar(16)` | NN; `ACTIVE`, `ARCHIVED` |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |
| `archived_at` | `timestamptz` | nullable; required exactly when status is `ARCHIVED` |

Constraints: composite FK to `projects`, `UNIQUE (tenant_id, project_id, flag_key)`, `UNIQUE (tenant_id, project_id, id)`, and `UNIQUE (id, value_type)`. The unqualified unique constraint permanently reserves an archived key.

### `flag_revisions`

Source of truth for versioned flag configuration. `value_type` is copied from the parent under composite FK control so child variant type checks remain local and enforceable.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `feature_flag_id` | `uuid` | NN |
| `revision_number` | `bigint` | NN, check `>= 1` |
| `value_type` | `varchar(16)` | NN, same as parent flag |
| `lifecycle_state` | `varchar(16)` | NN; `DRAFT`, `PUBLISHED` |
| `default_variant_key` | `varchar(128)` | NN |
| `rollout_seed` | `text` | NN, non-empty |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |
| `published_at` | `timestamptz` | nullable; required exactly when state is `PUBLISHED` |

Constraints:

- `(tenant_id, project_id, feature_flag_id) -> feature_flags (tenant_id, project_id, id)`.
- `(feature_flag_id, value_type) -> feature_flags (id, value_type)`.
- `UNIQUE (feature_flag_id, revision_number)`.
- `UNIQUE (tenant_id, project_id, feature_flag_id, id)`.
- `UNIQUE (id, value_type)` for typed child references.
- Deferred FK `(id, default_variant_key) -> flag_variants (revision_id, variant_key)` added after both tables exist.

Revision numbers are allocated while locking the parent flag or through a per-flag sequence strategy; `MAX(revision_number) + 1` without locking is forbidden.

### `flag_variants`

| Column | Type | Rules |
| --- | --- | --- |
| `revision_id` | `uuid` | PK part, NN |
| `variant_key` | `varchar(128)` | PK part, NN, key pattern |
| `value_type` | `varchar(16)` | NN |
| `value` | `jsonb` | NN |

Constraints: composite FK `(revision_id, value_type) -> flag_revisions (id, value_type)`. A check ties `jsonb_typeof(value)` to `value_type`: `boolean`, `string`, `number`, or `object`. JSON arrays and JSON null are not valid `OBJECT` variants. Update and delete are rejected when the parent revision is published.

### `targeting_rules`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `revision_id` | `uuid` | FK `flag_revisions`, NN |
| `priority` | `integer` | NN, check `>= 0` |
| `result_type` | `varchar(16)` | NN; `VARIANT`, `ROLLOUT` |
| `result_variant_key` | `varchar(128)` | nullable; required only for `VARIANT` |

Constraints: `UNIQUE (revision_id, priority)`, `UNIQUE (revision_id, id)`, and optional composite FK `(revision_id, result_variant_key) -> flag_variants`. `ROLLOUT` rules require no direct variant key and at least one complete allocation set.

### `rule_conditions`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `rule_id` | `uuid` | FK `targeting_rules`, NN |
| `condition_order` | `integer` | NN, check `>= 0` |
| `attribute` | `varchar(255)` | NN, non-blank |
| `operator` | `varchar(32)` | NN, Phase 0D operator set |
| `operand` | `jsonb` | nullable |

Constraints: `UNIQUE (rule_id, condition_order)`. `EXISTS` and `NOT_EXISTS` require SQL `NULL` operand; every other operator requires a non-null operand. `IN` and `NOT_IN` additionally require a non-empty JSON array. Conditions in a rule are combined with logical AND in ascending `condition_order`.

### `rollout_allocations`

| Column | Type | Rules |
| --- | --- | --- |
| `rule_id` | `uuid` | PK part, NN |
| `variant_key` | `varchar(128)` | PK part, NN |
| `revision_id` | `uuid` | NN |
| `basis_points` | `integer` | NN, check `1..10000` |
| `allocation_order` | `integer` | NN, check `>= 0`; preserves rollout bucket range order |

Constraints: `(revision_id, rule_id) -> targeting_rules (revision_id, id)`, `(revision_id, variant_key) -> flag_variants (revision_id, variant_key)`, and `UNIQUE (rule_id, allocation_order)`. A deferred constraint trigger validates that every `ROLLOUT` rule totals exactly 10,000 basis points before commit. Published parents block mutation. Snapshot compilation emits allocations in ascending `allocation_order`; changing that order changes bucket ownership and therefore requires a new revision.

## Publication

### `environment_flag_states`

The authoritative current selection for one flag in one environment.

| Column | Type | Rules |
| --- | --- | --- |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `environment_id` | `uuid` | PK part, NN |
| `feature_flag_id` | `uuid` | PK part, NN |
| `revision_id` | `uuid` | NN, published revision only |
| `enabled` | `boolean` | NN |
| `environment_version` | `bigint` | NN, check `>= 1` |
| `updated_at` | `timestamptz` | NN |

Composite FKs guarantee that the environment, flag, and revision share tenant and project scope and that the revision belongs to the flag. The row may change only inside a successful publication transaction. `environment_version` records which environment CAS version last changed this flag state.

### `configuration_snapshots`

Immutable full configuration artifact for one environment version.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN; also Phase 0D `snapshotId` |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `environment_id` | `uuid` | NN |
| `snapshot_version` | `bigint` | NN, check `>= 1` |
| `schema_version` | `integer` | NN, check `>= 1` |
| `payload` | `jsonb` | NN, JSON object; compiled full snapshot payload |
| `checksum` | `char(64)` | NN, lowercase hexadecimal |
| `generated_at` | `timestamptz` | NN |

Constraints: composite FK to environment, `UNIQUE (environment_id, snapshot_version)`, `UNIQUE (tenant_id, id)`, `UNIQUE (tenant_id, project_id, environment_id, id)`, and optionally `UNIQUE (environment_id, snapshot_version, checksum)` for idempotency diagnostics. Payload contains the complete Phase 0D document including its top-level checksum, passes the schema and semantic validator before insert, and must agree with the relational checksum column. Checksum calculation removes the top-level field and uses RFC 8785 plus SHA-256. Database permissions and triggers reject update/delete.

### `snapshot_entries`

Relational lineage for each flag embedded in a compiled snapshot.

| Column | Type | Rules |
| --- | --- | --- |
| `snapshot_id` | `uuid` | PK part, FK `configuration_snapshots`, NN |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `environment_id` | `uuid` | NN |
| `feature_flag_id` | `uuid` | PK part, NN |
| `revision_id` | `uuid` | NN |
| `enabled` | `boolean` | NN |

Composite FKs `(tenant_id, project_id, environment_id, snapshot_id)` and `(tenant_id, project_id, feature_flag_id, revision_id)` retain tenant/project consistency through snapshot and revision alternate keys. The payload is the immutable distributed artifact; entries provide relational traceability and history queries and must be created in the same transaction.

## Distribution administration

### `client_applications`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `environment_id` | `uuid` | NN |
| `client_application_key` | `varchar(128)` | NN, key pattern |
| `lifecycle_status` | `varchar(16)` | NN; `ACTIVE`, `ARCHIVED` |
| `created_at` | `timestamptz` | NN |
| `updated_at` | `timestamptz` | NN |
| `archived_at` | `timestamptz` | nullable |

Constraints: composite FK to environment, `UNIQUE (tenant_id, project_id, client_application_key)`, and alternate key `UNIQUE (tenant_id, project_id, id)` for credential ownership. One application is authorized for exactly one environment in v1.

### `service_credentials`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN; public credential identifier |
| `tenant_id` | `uuid` | NN |
| `project_id` | `uuid` | NN |
| `client_application_id` | `uuid` | NN |
| `secret_hash` | `text` | NN; PHC-formatted Argon2id hash or approved equivalent |
| `secret_prefix` | `varchar(16)` | NN; non-secret operator hint |
| `status` | `varchar(16)` | NN; `ACTIVE`, `REVOKED` |
| `created_at` | `timestamptz` | NN |
| `expires_at` | `timestamptz` | nullable |
| `revoked_at` | `timestamptz` | nullable; required exactly for `REVOKED` |

Constraints:

- Composite FK `(tenant_id, project_id, client_application_id) -> client_applications (tenant_id, project_id, id)` with `ON DELETE RESTRICT`.
- `status = 'ACTIVE'` requires `revoked_at IS NULL`; `status = 'REVOKED'` requires `revoked_at IS NOT NULL`.

The composite FK is mandatory even though `client_application_id` is a globally unique UUID: it prevents a credential that declares Tenant/Project A from referencing Tenant/Project B's application. Only `id`, prefix, hash, and lifecycle metadata are stored. The raw secret is returned once by the issuance API and is never logged, audited, or persisted. Rotation creates a new credential row and revokes the old row.

## Traceability and reliable messaging

### `audit_events`

Append-only business history.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN |
| `tenant_id` | `uuid` | FK `tenants`, NN |
| `actor_type` | `varchar(16)` | NN; `USER`, `SERVICE`, `SYSTEM` |
| `actor_id` | `varchar(255)` | NN |
| `action` | `varchar(100)` | NN |
| `resource_type` | `varchar(100)` | NN |
| `resource_id` | `uuid` | NN |
| `correlation_id` | `uuid` | NN |
| `details` | `jsonb` | NN, default `{}`; descriptive metadata only |
| `created_at` | `timestamptz` | NN |

Application roles receive INSERT and SELECT but no UPDATE or DELETE. Trigger protection remains as defense in depth. Secret material and high-cardinality evaluation context are forbidden in `details`.

### `outbox_events`

Transactional delivery intent for Kafka notification.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | PK, NN; stable event identity |
| `tenant_id` | `uuid` | FK `tenants`, NN |
| `snapshot_id` | `uuid` | FK `configuration_snapshots`, NN |
| `aggregate_type` | `varchar(64)` | NN |
| `aggregate_id` | `uuid` | NN |
| `event_type` | `varchar(100)` | NN |
| `event_version` | `integer` | NN, check `>= 1` |
| `payload` | `jsonb` | NN, JSON object |
| `created_at` | `timestamptz` | NN |
| `published_at` | `timestamptz` | nullable |
| `attempt_count` | `integer` | NN, default `0`, check `>= 0` |
| `next_attempt_at` | `timestamptz` | NN |
| `last_error` | `text` | nullable, bounded by application before persistence |

Event identity, ownership, type, version, payload, and creation time are immutable. The relay claims pending rows with `FOR UPDATE SKIP LOCKED`, publishes at least once, and updates only delivery metadata.

The FK `(tenant_id, snapshot_id) -> configuration_snapshots (tenant_id, id)` prevents a delivery intent from referencing another tenant's snapshot.

## Cross-table enforcement matrix

| Invariant | Database enforcement | Additional service enforcement |
| --- | --- | --- |
| Tenant/project ownership | Denormalized scope plus composite FK | Authorized principal supplies scope to every repository call |
| Stable archived keys | Non-partial unique constraints | Archive transition validation |
| Typed variants | Composite type FK plus `jsonb_typeof` check | Phase 0D semantic validator |
| Valid default/result/allocation references | Composite and deferred FKs | Authoring validation with clear error response |
| Allocation total 10,000 | Deferred constraint trigger | Semantic validation before publish |
| Published revision immutable | Parent-aware triggers and restricted privileges | Domain state transition guard |
| Snapshot version monotonic | Environment CAS plus unique `(environment_id, snapshot_version)` | Expected-version conflict mapping |
| Snapshot/audit immutable | Insert-only privileges and triggers | No mutation API |
| Credential raw secret absent | No plaintext column | One-time response, log redaction, hashing before persistence |
| Credential tenant/project ownership | Composite FK to `client_applications` | Cross-tenant credential association negative test |
| Publication atomic | One database transaction | Transaction boundary in publication application service |

## Delete and archive policy

- Tenant, project, environment, flag, and client application identities use archive semantics once referenced.
- Archived keys remain reserved because unique constraints are not partial.
- Draft revisions that have never been published may be deleted only through an explicit authoring operation and only when no snapshot or environment state references them.
- Published revisions, snapshots, snapshot entries, audit events, revoked credentials, and pending/failed outbox events are never cascade-deleted.
- Foreign keys default to `ON DELETE RESTRICT`; `CASCADE` is limited to disposable draft children deleted together with an unpublished draft.
